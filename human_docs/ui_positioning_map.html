How the UI knows where things are

Every selectable element has two positions that never meet in the code: a small grid position that decides where the joystick goes, and a pixel rectangle that decides where it is drawn. The figures use the RACK tab on a 128 × 128 screen, with the real numbers.

Where the pixel rectangles come from

Nothing is typed in as a coordinate. layout() starts from the area under the header and cuts it up with the style's spacing, so the same code gives a different result on a different screen.

How the joystick picks the next element

nav() never looks at pixels. It works on row, column and span, and it skips elements that are disabled.

left / right : same row, the element with the smallest gap in that direction up / down : the nearest row in that direction that has an enabled element, then the element whose columns overlap the current one (first listed wins a tie) nothing above the first row -> the header header + down -> the first enabled element encoder A : plain table order, header included, wrapping around

The list-and-picture tabs

GENERAL, SAMPLES, FX RACK and the FM tabs share one layout, ui_layout_column(). Here the grid position is not used for placing at all: the n-th element simply becomes the n-th row.

One number is still typed in: the top of the picture box (14) assumes the header is 9 px tall plus its rule. A different font or padding would move the header and not that number.

Who reads what, and the weak point

The two are not connected. nav() trusts the typed row and col. layout() trusts its own arithmetic. In the RACK tab the arithmetic reads the typed numbers back to build the grid, so they agree. In the list-and-picture tabs the layout stacks elements in table order and ignores them, so they agree only because every element has col 0 and a row equal to its index.

The fix: navigate by rectangles

Today

element table Tgt row 2, col 0 <- typed Prm row 2, col 1 <- typed layout() -> where to draw nav() -> where to go, from the typed numbers Move an element in layout() and the joystick does not follow.

Proposed

element table Tgt (no position) Prm (no position) layout() -> the only place with a position nav() -> picks the nearest rectangle in the pressed direction Move an element in layout() and the joystick follows.

The rectangles already exist on every frame, so navigation would use them as they are: from the focused rectangle, the nearest neighbour whose centre lies in the direction pressed, skipping disabled elements. The row, column and span fields would be deleted, and every new screen would need one position fewer to get right.
