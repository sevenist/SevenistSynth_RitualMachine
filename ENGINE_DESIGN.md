# SynthCore engine: design document (living)

Own DSP engine to replace AMY step by step. Source of truth for decisions; update it every stage.
Code: `src/engine/` (portable C++17, no AMY/SDL/Arduino includes). Tests: `tests/engine/`,
run with `.\tools\build_engine_tests.ps1 [-Sr 44100 -Block 64]`.

## Goals

Dynamic modular synth with audio-rate routing and complex modulation paths, q15 optimised, own DSP
modules (multipole filters, saturation, FX bases, FFT effects, delay, chorus, algorithmic reverb) and a
sampling engine with dynamic pre-caching for slow storage (TF card, PSRAM, flash).
First target ESP32-S3 (FPU present, but not required), desktop simulator is first class.

## Decisions (ADRs)

### ADR-001: Language and boundaries (Accepted)
C++17 core under `src/engine/`, no exceptions, no RTTI, **no heap allocation after init** (arenas, ADR-005).
The rest of the project is C: the engine is exposed through a small `extern "C"` header. Existing `core/`
stays C and never includes engine C++ headers.
*Why:* templates/constexpr for kernels and tables, deterministic memory; C boundary keeps `core/` portable.
*Rejected:* plain C (no templates, macro soup for kernels), full C++ rewrite of core/ (churn without gain).
*Consequence:* `build.ps1` and PlatformIO need to compile `.cpp` (done when the engine is integrated, stage 7).

### ADR-002: Numeric representation (Accepted)
Audio buffers are **q15** (`int16_t`). Internal state (filters, envelopes, feedback paths, delay
accumulation) is **q31** with `int64_t` products where needed; coefficients with range > 1 use an explicit
Q format through `mulq(a, b, shift)`. Phases are `uint32_t`. Float is allowed at init/control rate and in
tests only. All helpers saturate and round to nearest (`engine/dsp/q.h`).
*Why:* low-frequency filters and long reverb tails are noisy/unstable with 16-bit state; half the RAM of
q31 buffers; fast on LX7 (single-cycle 32x32->64 on S3), still works on FPU-less targets.
*Rejected:* strict q15 state (limit cycles, noise), float/q15 compile-time switch (doubles test matrix).
*Risk:* scaling bugs. Mitigation: every module gets an SNR test against a float64 reference.

### ADR-003: Graph model (Accepted)
The rack is compiled on the UI/control side into a flat **execution plan** (array of steps: module, input
and output buffer ids, parameter block). Buffers are pooled by liveness analysis. Each voice instantiates
the voice sub-graph; FX run once on the summed bus. The plan is swapped atomically at a block boundary.
Feedback is allowed only through an explicit one-block delay. Audio-rate FM/AM/ring modulation are plain
audio connections. Details (port types, modulation matrix) are decided at stage 2.
*Rejected:* shared paraphonic graph (limited per-voice modulation), per-sample interpreter (3-5x slower).

### ADR-004: Sample rate and block size (Accepted)
`ENGINE_SR` (default 48000) and `ENGINE_BLOCK` (default 32, power of two 8..256) are compile-time
constants in `engine/dsp/config.h`. All coefficients and time constants derive from them; nothing may
hardcode 48000 or 32. Tests run in two configurations (48k/32 and 44.1k/64). Control rate = SR / BLOCK.
Mono voices, stereo FX bus.

### ADR-005: Memory (Accepted, implementation in `core/arena.h`)
Bump arenas over caller-provided memory, `mark()/rewind()` to build and discard candidate plans, high-water
mark for the budget table. Allocation failure latches `failed()`; modules must tolerate `nullptr`.

### ADR-006: Pitch, exponentials and sine (Accepted, `dsp/phase.h`, `dsp/tables.*`)
Pitch is `int32` in 1/256 semitone. One shared primitive `exp2_scale(base, x_q16_octaves)`: 256-entry
unsigned Q2.30 table + linear interpolation (measured error below 0.2 cent), used for pitch, cutoff,
envelope times and LFO rates. Sine is a 1024-entry q15 table + linear interpolation (measured error
under 2 LSB, SNR over 80 dB). Tables are generated by `tools/gen_engine_tables.py` and committed (flash, 3 KB).
*Rejected:* polynomial exp2 (more multiplies, harder to verify), 4096-entry tables (16 KB competing with the
ESP32 cache), parabolic sine (-50..-70 dB distortion, audible in FM).

### ADR-007: Smoothing (Accepted, `dsp/smooth.h`)
Both kinds, per parameter type: `Ramp` (linear, exact target after n samples) for gains, mixes, pitch and
anything retargeted once per block; `OnePole` (exponential, snaps when the step rounds to 0) for knobs
without a deadline. Cutoff is ramped in the log (Q16 octave) domain so sweeps sound even.

### ADR-008: Control-time heap (Accepted, `core/heap.*`)
Because module state survives rebuilds, instances live and die at different times, so a bump arena is not
enough. A first-fit heap with coalescing (16-byte aligned, zero-filled) serves plan compilation and module
creation. It is never called from the audio path. `Arena` stays for init-time one-shot allocations.

### ADR-009: Module API (Accepted, `core/module.h`)
Abstract class created with placement-new in the heap; one virtual `process(ctx, ports)` per module per
block. Static `ModuleInfo` (scope, port counts, parameter descriptors) lets the compiler and the UI discover
ports and parameters. Parameters are int32 in module-defined units.
*Rejected:* POD function tables (type-unsafe state), static templates (contradicts the dynamic rack).

### ADR-010: All signals are q15 audio-rate blocks (Accepted; user override of my recommendation)
Audio, control and modulation use the same `q15[kBlock]` buffer, so any output can drive any input.
*My recommendation was two rates (audio + 1 value per block) for CPU.* The risk is the cost of slow
modulators (LFO, envelope, step lane) rendered at full rate per voice, roughly 20-30 % on mod-heavy patches.
*Mitigations planned:* modules keep q31 state internally (only the output block is q15, 1 LSB is 0.0003 octave on
a 10-octave cutoff range, inaudible), and a later "constant block" hint on buffers so consumers can skip
per-sample work. Re-measure on hardware before adding either.

### ADR-011: Parameters and modulation are cables with depth (Accepted, `core/graph.h`, `core/plan.*`)
Every input and every parameter accepts up to `kMaxFanIn` (8) cables, each with a signed q15 depth. A single
unity-depth cable is aliased (no copy); anything else becomes a MIX step. A parameter's `mod[p]` buffer is
the weighted sum, bipolar, full scale = the module's own range, added to the parameter's base value.
Modulating modulators and modulator depth is therefore just another cable. Closing a loop requires a
`delayed` cable (one-block delay, per-voice buffers for voice scope; verified by test).
Execution order per block: global-pre, each active voice, global-post (modules with `reads_bus`).
A voice module cannot feed a global module directly (only through `VoiceOut`), and a voice input cannot read
the voice sum without a delayed cable.

### ADR-012: Live edits keep state by node id (Accepted, `core/engine.*`)
`load()` compiles a new plan off-line and publishes it atomically; `render()` swaps at the next block start.
Instances with the same `(id, type)` are reused (filter memory, delay tails, counters survive); new nodes start
fresh; `gc()` frees retired plans and unreferenced instances. Voices are not cut by a rebuild.
*Not done yet:* 1-block crossfade at the swap (parameter-driven clicks are possible), event queue between the
UI and audio threads (stage 7). Callers must serialise `load/note_*/set_param` against `render` until then.

### ADR-013: Saturation is naive, with an anti-aliasing seam (Accepted; user override of my recommendation)
`Shaper` (tanh table, hard clip, sine fold, bit crush) applies the nonlinearity directly with no
anti-aliasing. *My recommendation was first-order ADAA.* Risk: audible aliasing on bright, hard-driven signals.
The shaper's per-sample core is a pure function of (x, drive), so ADAA or 2x oversampling can be added behind
the same module without changing graphs. Revisit when listening on hardware.

### ADR-014: Filter = TPT/ZDF state-variable cascade (Accepted, `dsp/svf.h`, `Filter` module)
Q28 signal/state (+-8.0 headroom: a saturating state acts as a limiter instead of wrapping), Q31 coefficients
a1..a3 (all below 1), Q29 damping k. g = tan(pi fc/fs) from a 234-entry table; 1/(1+g(g+k)) by a
division-free Newton reciprocal (measured error 1.2 LSB of Q31), so a coefficient update costs about 25
multiplies and runs **per sample only when a cable is connected to the cutoff**, otherwise once per block with
control-rate smoothing of knob moves. 1..4 sections = 12..48 dB/oct with Butterworth Q per section; resonance
multiplies the Q of the last section (up to 16x). LP/BP(normalised, 0 dB at centre)/HP/notch.
Measured: LP response within 0.4 dB of the analytic bilinear Butterworth for 1..4 sections, HP, BP, notch.
Cutoff is a pitch value (MIDI*256), so key tracking is just a cable from NoteIn.

### ADR-015: Oscillators = PolyBLEP / PolyBLAMP (Accepted, `dsp/osc.h`, `Osc` module)
Saw and pulse use PolyBLEP, triangle PolyBLAMP (residual = slope change x (1-|x|)^3 / 6), sine the 1024 table,
noise xorshift. Phase and per-sample increment are uint32, so audio-rate pitch FM (a cable into the `pitch`
parameter) costs one `pitch_to_inc` per sample. Measured alias level vs naive: saw 16 dB lower at 1.2 kHz and
15 dB at 5 kHz, pulse 17 / 13 dB, triangle 13 / 10 dB. FM test: a 1 kHz carrier modulated by 100 Hz matches
Bessel theory (sidebands -8.6 dB, second order -23.3 dB). Pulse keeps its +-1 levels, so it carries a DC offset
of 2*duty-1 (removing it would clip narrow pulses). A wavetable oscillator is a later separate module.

### ADR-016: FFT = q15 block floating point, N = 512; one STFT framework (Accepted; user override of my recommendation)
Radix-2 DIT complex FFT on int16 re/im, a full-block scan before each stage shifts just enough to keep the
butterfly growth inside int16, exponent returned (`true = stored * 2^exp`). *My recommendation was q31 data
and N = 1024 for about 20 dB more SNR.* Measured on the q15/BFP version: 67 dB vs a double DFT on
white-noise-like data, 58 dB on an FFT + IFFT round trip, 61 dB on a quiet (amplitude 300) signal thanks
to the block scaling, STFT identity 71 dB. The risk I flagged (noise floor around -70 dB) is real but
acceptable; revisit if spectral freezes on quiet material sound grainy. `kFftN` and the generated twiddle
tables are tied together by `tools/gen_engine_tables.py` (FFT_N).
`Stft` (`dsp/stft.h`): sine window, hop N/4, overlap-add, mono (Hermitian, callback edits bins 0..N/2) or dual
(second input packed into the imaginary part). Latency is exactly N = 512 samples (measured), 10.7 ms at 48 kHz.
**Limit:** at 96 kHz the 187 Hz bins are too wide for the phase-vocoder effects (freeze, pitch shift); use N = 1024
there (requires regenerating the tables). The tests skip those two checks above 48 kHz.
**Addendum (2026-10-07, measured on the S3; the user chose "own PIE block-float kernel" over ESP-DSP int16 / float).**
The first board measurement showed the C FFT at 205k cycles per transform (fastest run; 300-450k as boot averages
with preemption), so an STFT hop (2 transforms) needed more than a core: SpectralFx / Vocoder could never have run on
the board. Measured candidates (one 512 complex transform, SNR loud / quiet / very quiet noise vs a float DFT):
C BFP 173k (after an exact rewrite: the per-stage scan folded into the butterflies, bit-identical, test
`fft_is_bit_identical_to_the_reference`) 67 / 60 / 37 dB; ESP-DSP int16 PIE 26k 53 / 46 / 47 dB (fixed 1/2 per stage);
ESP-DSP float radix-2 63k 84 / 76 / 53 dB; ESP-DSP float radix-4 needs a power of 4 (512 is not).
**As built:** `dsp/fft_s3.S` = PIE stages after ESP-DSP's structure (credited in THIRD_PARTY_NOTICES.md) with our
block floating point: `SAR = 14 + shift`, q14 twiddles in bit-reversed order (sign -1: +1 mirrors the spectrum), per-lane
vmax / vmin of each stage's outputs choose the next shift; PIE pack (min / max, scale, interleave) and a scalar
bit-reversal unpack. The input is first scaled up to the safe level (exponent may go negative) because the PIE shifts
truncate: without it a quiet frame lost 9 dB. **16.0k cycles per transform (10.9x), 63 / 64 / 63 dB, exponent exact,
round trip 59.6 dB; Stft identity on the board 71.6 dB (host C: 71.4).** `fft_q15` uses it when `SC_FFT_PIE`
(ESP32-S3); every other target keeps the C version (`fft_q15_c`). Frames must be 16-byte aligned for the PIE pack
(the engine heap is; otherwise a scalar pack runs). The Stft overlap-add lost its 64-bit multiply / shift (exact,
checksum-identical). Stft mono with an identity frame: **517 cycles per sample** (9.5 % of a core at 44.1 kHz;
a frame 62.7k = 32k FFTs + 31k window / mirror / overlap-add). Remaining: the window and overlap-add loops and the
bit-reversal unpack (4.7k per transform) are scalar. Risk: PIE assembly is S3-only and checked by the boot bench, not
by the host tests (the host runs the C path).
Later the same day: the window (`pie_vmul_s16`), the overlap-add (`pie_ola_*`, bit-identical) and the phase vocoder's CORDIC
(`pie_cordic`, bit-identical; analysis 39k -> 17k per frame) went to PIE as well: Stft frame 40.4k, 333 cycles per sample.
`ee.vmul.s16` truncates and wraps (measured). SpectralFx is in the FX rack (type Spectral, stereo mode: STFT on the mono sum,
dry per channel). Startup patch + Pitch +7: 66 % of the budget and **0 DMA underruns**; ~190 renders per 4 s exceed the
64-frame budget because a frame lands on every other write, but the 6 x 64 DMA ring absorbs them (`[AUDIO] DMA underruns`).
CORDIC (`dsp/cordic.h`, 16 iterations): phase error 0.0017 deg, magnitude within output rounding.

### ADR-017: Two memory classes (Accepted, `Memory{fast, bulk}` in `core/module.h`)
Modules receive both heaps in `init()`. Delay lines allocate from `bulk` (verified by a test with a separate
heap standing in for PSRAM; the fast heap only holds plan and module objects), STFT frames and phase-vocoder
state from `fast`. Both pointers may alias on the desktop. Sample caches (stage 6) use `bulk` too.

### ADR-018: Effect modules (`modules/fx_modules.*`)
- **Delay** (stereo, global): time in 1/16 ms up to `ENGINE_DELAY_MAX_MS` (default 1000), Hermite reads, damped
  feedback (one-pole in the loop), ping-pong, time cable. Time changes glide with the delay moving at most
  1/4 sample per sample (a +-25 % tape-like pitch swoop, never a click; a 100 -> 400 ms jump takes 1.2 s).
  Echoes measured on the exact sample (4800 / 9600 / 14400 at 100 ms).
- **SpectralFx** (mono): THRU, FREEZE (holds magnitude and phase advance, keeps the tone alive after the input
  stops), GATE (bins below a fraction of the frame peak, plus a lo..hi band), ROBOT (zero phase, buzz at fs / 128),
  WHISPER (random phase), PITCH (phase-vocoder bin remapping). Measured: pitch shifts land within 0.2 % of the
  target, gate lowers a -50 dB noise floor by 40 dB, a 3..8 kHz band keeps 6 kHz and removes 1 kHz by 94 dB.
  Basic phase vocoder: no phase locking, so transients and big shifts are phasey. The mix path has a delayed dry
  signal aligned to the 512-sample latency.
- **Vocoder** (dual STFT): the modulator's band energy (bands of 2..32 bins) scales the carrier's spectrum; both
  inputs go through one FFT. A 1 kHz modulator on white noise puts 58 dB more energy near 1 kHz than at 3 to 8 kHz.
- Budget: the estimate here (80k per hop) was 10x low: the C FFT alone was 2 x 173k per hop. Measured on the S3 with
  the PIE FFT (ADR-016 addendum): the STFT frame engine costs 333 cycles per sample (40.4k per hop). In the FX rack
  (stereo mode), per 64-frame block: Thru ~20k, Freeze ~33k, Pitch ~43k (analysis 8.5k, resynthesis 10.9k). The
  Vocoder is not in the rack (it needs a modulator signal).

### ADR-019: Chorus = fixed Juno-like modes (Accepted; user choice over my multi-voice recommendation)
`Chorus` (stereo): modes OFF, I (0.513 Hz), II (0.863 Hz), I+II (9.75 Hz, shallow). One Hermite-read line per
channel, triangle LFO with opposite phase on L and R, wet band-limited by a 9 kHz one-pole (BBD-like) and added to
the dry signal. Mode changes crossfade depth and gain, no click. Measured by cross-correlating the wet signal with
the dry noise: delay swings 1.56..5.13 ms in mode I (spec 1.54..5.15), mode II period 1.152 s (1.159), mode I+II
3.11..3.59 ms at 0.102 s (0.103); L and R delays always add up to twice the centre (opposite phase).
Not a flanger and not general: that needs a different module (the delay line and LFO are reusable).

### ADR-020: Reverb = Dattorro plate (Accepted; user choice over my FDN recommendation)
Input: pre-delay (bulk heap, up to 200 ms) -> bandwidth low-pass -> 4 allpass diffusers -> figure-8 tank (2 x
[modulated allpass, delay, damping low-pass, decay, allpass, delay]) -> 7 output taps per channel, the published
tap table of Dattorro 1997, every length scaled by fs / 29761. `size` (x0.5..x1.25) glides: the tank delays and
all taps are interpolated per sample and the delay never moves faster than about 1/6 sample per sample.
Lessons recorded in the code: (1) a rounding bias of half an LSB per pass becomes a DC offset in any feedback loop
with unity-gain paths (allpass, low-pass): `lerp15` rounds instead of flooring, each half has a DC blocker in
the loop and the outputs have one too; (2) stepping tap positions once per block jumps by several samples and
clicks. Measured: decay rate 65 / 43 / 16 dB/s for decay 0.30 / 0.50 / 0.79, identical at 32, 44.1, 48 and 96 kHz;
L/R correlation -0.01; high-frequency tail 20 dB lower with dark damping; stable at maximum decay with loud
noise; 88 KB of fast memory + 19 KB bulk at 48 kHz, 0.3 % of real time on the PC.
Known limit: the q15 tank has a rounding floor of about 2 LSB rms (-84 dBFS) in the tail (inaudible; a q31 tank
or dither would remove it).

### ADR-021: Sample container (Accepted, `sampler/smp_format.h`, `tools/wav2smp.py`)
Cooked `.smp`: a 4 KB header (rate, frames, root note, tune, loop points and mode, up to 16 slice starts) then mono
16-bit PCM in 4 KB blocks, so every read is sector aligned and nothing is parsed at run time. `wav2smp.py` takes
8/16/24/32-bit WAV, mixes stereo down, reads the `smpl` loop chunk, writes slices; verified against the C++ parser.
Bandwidth is 96 KB/s per voice at 48 kHz. Not done: stereo samples, ADPCM (the format has a version field for both).

### ADR-022: Streaming = RAM heads + per-voice ring + earliest-deadline-first loader (Accepted, `sampler/*`)
- `StorageDevice` (`sampler/storage.h`): asynchronous `submit` / `poll`, never blocks. `SimStorage` (`platform/sim/sim_storage.h`) models a slow serial
  card (latency, bandwidth, periodic stalls) against an explicit clock, so every streaming behaviour is reproducible
  in tests. The ESP32 TF-card / PSRAM / flash drivers implement the same interface (stage 7).
- `SampleBank::load(name, head_ms)`: keeps the first `head_ms` (default 150), a short head for every slice, and a tail
  head (reverse playback starts at the end) in bulk RAM; `head_ms = 0` makes a sample fully resident (granular).
  Notes and slice triggers therefore start in the very first block whatever the card latency (tested with 40 ms).
- Every Sampler voice owns a `Stream`: a ring of `ENGINE_RING_BLOCKS` (12, was 8: addendum 2) blocks = 48 KB in bulk RAM. Audio thread
  and loader share only atomics; each ring slot is tagged `(generation, block)` so a block read for an old note can
  never be played for a new one. The loader walks the playback path (loops, ping-pong, reverse) in half-block steps,
  always includes both loop endpoints when the path wraps, and issues reads for the stream whose first missing
  block is needed soonest (`kQueueDepth` = 2 outstanding).
- Underrun policy: the output holds its last value, decays 1/64 per sample, the timeline keeps running, and on
  recovery crosses over to the live signal in 64 samples: continuous at both ends (measured: largest step 1017 vs 922 for
  a plain sine through four 400 ms card stalls). Every episode increments `SamplerStats::underruns`.
- Measured at 48 kHz: a 3 s sample over a 15 ms / 2 MB/s card plays with SNR 92 dB and 0 underruns (288 KB read);
  4 voices on 4 different 2 s samples over a 1.5 MB/s card, 0 underruns; the same on a 120 KB/s card reports 5.
- Lessons: (1) sampling the read-ahead path once per block missed the block that contains the loop start (3 underruns
  per loop lap) -> half-block steps plus explicit endpoints; (2) reverse start needs a tail head; (3) a start offset
  or a retrigger beyond the RAM head needs data the card cannot deliver in time, which is physics, not a bug.

### ADR-023: Sampler and Granular modules (Accepted, `modules/sampler_modules.*`)
`Sampler` (voice): pitch CV like the oscillator (or fixed-speed playback for drums), Hermite or linear resampling in
Q32 positions, loops (file default / off / forward / ping-pong), reverse, start offset, slices (start at slice n, stop
at the next one), instruments with key/velocity zones (zone sample, root, tune, gain), pitch FM. `Granular` (voice or
global): up to 16 grains from a resident sample with position, speed (0 = freeze, negative = backwards), size, density,
pitch, jitter, Hann windows, randomised onsets. *Randomised onsets are essential:* a regular grain train is a comb
filter that turned a 440 Hz tone into the 7th harmonic of the 60 grains/s rate (420 Hz).

### ADR-024: Threading = SDL / DMA audio thread + lock-free command queue (Accepted, `core/command_queue.h`, `core/engine.*`)
`Engine::render()` runs on the audio thread (SDL callback on the desktop, a task pinned to core 1 on the ESP32). Every
control call that touches sounding state (`note_on`, `note_off`, `all_notes_off`, `set_param`, `set_blob`) only posts a
fixed-size command into an SPSC ring (512 slots, `false` when full); `render()` drains it at the start of each block.
`load()` compiles a plan on the control thread and publishes it with one atomic pointer. `render()` switches at the next
block start and, at that moment, applies the new parameter values of the module instances the two plans share, so a
rebuild never changes a module mid-block. Plans the audio thread has finished with go onto a lock-free stack that `gc()`
empties; `gc()` reads the two live plans under a seqlock (the audio thread bumps a counter around the switch) and backs
off when it overlaps. A stress test runs 2.5 s of continuous rendering against about 195k rebuilds and 290k commands:
no crash, no leak (heap back to 0 after shutdown). Two bugs it found and fixed: retired plans were dropped when more
than four accumulated between `gc()` calls; and the first design let `gc()` free instances in the window between the
audio thread taking the pending plan and publishing it.
Note: commands are applied at the next block, so a note-on and note-off posted in the same block never open the gate.

### ADR-025: DX7-style FM voice in the engine (Accepted, `modules/dx7_voice.*`, `platform/engine/dx7_convert.*`)
Replacing AMY removed the only FM implementation, so the engine got its own: one module per voice, the MSFA algorithm
wiring (32 tables, copied from AMY's `algorithms.c`), operator output `amp*sin(2 pi(phase + modulation + feedback))` with
modulation in cycles, feedback from the averaged raw sine, carriers x 1/4 x velocity, envelopes linear in the DX7 level
domain (2^((L-99)/8) amplitude, stepped once per block, interpolated across it). The whole patch travels as a blob
(`Engine::set_blob`) built by `dx7_convert` from the editable `dx7_patch_t`. Measured: first and second sideband of a
two-operator pair at -4.8 / -16.5 dB (Bessel theory -4.8 / -16.5), feedback 1 puts the second harmonic at -3 dB (0 -> -86 dB),
envelope law within 0.1 dB, all 32 algorithms sound, all 128 factory patches play. The per-patch loudness trim table
(`platform/engine/fm_patch_gain.h`) is regenerated by the test (`DX7_GAIN_OUT=...`); it is within 20 % of the old AMY
table in shape, which confirms the voice reproduces AMY's relative loudness.
Differences from the AMY-based version: no AMY extra shaping of rising envelope segments, no factory LFO / pitch EG /
velocity sensitivity (as before); the envelope runs at block rate (coarse at block sizes of 256 and above).

### ADR-026: Rack -> graph mapper, always-on master effects (Accepted, `platform/engine/rack_graph.*`)
`rack_graph_build()` turns `rack_t` + the amp envelope + general settings into a `GraphDesc` with the previous semantics:
audio modules in slot order, a source (OC) adds to the running signal (levels x 1/sqrt n; since 2026-10-06 every source is a cable into the next module's input and the plan's MIX step sums them in one pass with one saturation, no Mix4 chain; more than `kMaxFanIn` sources fold the first eight into one pass-through Mix4), a
processor (FL, SA) acts on everything to its left, a processor with nothing before it is dropped, an ENV aimed at a cutoff
replaces the filter's own envelope, modulators are cables whose depth is the effect per unit of module depth divided by the
target's full-scale range. Node ids come from the rack module ids, so editing the rack keeps the state of untouched
modules. Not realised (as before): resonance and mix modulation, modulating a modulator (MS: see ADR-029; an OC with a target: ADR-028). The master chain
BusIn -> Chorus -> Delay -> Reverb -> MasterOut is always in the graph and driven by two new menu tabs (FX 1: chorus mode,
delay mix / time / feedback; FX 2: reverb mix / decay / size / damp / pre-delay), so every effect edit is a live parameter
message, never a rebuild. `engine_synth_set_params()` rebuilds the description and sends only the parameter differences
(or reloads when the structure or a cable depth changed).

### ADR-027: AMY removed, new build (Accepted)
`lib/amy` and `src/platform/amy` are no longer used (AMY is only read by `tools/gen_dx7.py`, to regenerate the DX7 tables).
`build.ps1` compiles every file to its own object in `build/obj` with dependency tracking and 16 parallel jobs: a clean
build takes about 5 s (was 35 s), a one-file change 1.5 s. The engine is C++17 (`g++ -fno-exceptions -fno-rtti`), the
rest C; `-Clean` forces a full rebuild.

### ADR-028: An oscillator with a target modulates at its own pitch and stays in the chain (Accepted, `rack_graph.cpp`, `core/rack.c`)
The old "OC with a target" was a separate control-rate oscillator with its own `Rate` in Hz, out of the audio chain. Now an
OC is always a source in the chain; giving it a target additionally routes its own output (wave, Crs / Fine, note pitch, PW)
into that parameter with the cable depth `0.5 x Dpth / range` (full-scale pitch cable = +-12 semitones, so Dpth 2 is the
maximum). The oscillator then runs at full level and the depth of its cable into the chain applies `Lvl` (and the 1/sqrt n source scaling; `qd()`, never exactly unity, so a level edit stays a live `SetDepth`) on its
way into the chain, so the modulation signal does not depend on `Lvl`; the `Out` switch on the OSC MOD page (`On` / `Mute`)
sets that cable's depth to 0 (the MIX step skips zero gains) while the modulation cable stays untouched. Mute only counts while the target exists in the rack.
Consequence: `MP_OC_RATE` is gone (the slot value index became `MP_OC_MUTE`); an OC that used to be silent in the chain
because it had a target is now audible until it is muted.

### ADR-029: Motion sequencer (Accepted, `modules/motion_seq.*`, `core/rack.*`, `core/synth_ui.c`; user choices: engine clock, per-lane polarity, pool of 2)
A global-scope engine module `MotionSeq` with 4 outputs (lane 1..4) feeding voice-scope parameters as ordinary cables
(a global module may feed a voice module, not the reverse). Lane data (16 values 0..100, an active bit per step, STEP /
LINEAR, bipolar / unipolar) travels as one `MotionBlob` with `set_blob`; target, depth and the rest stay in `rack_t`
(`ms_pattern_t ms[2]`, the MS slot's `v[0]` is its pool index; a third MS cannot be inserted).
- **Clock in the engine, sample-accurate.** The module counts frames from a restart point using the *same integer-ms rules as
  `seq.c`* (step = 15000 / bpm ms, swing lengthens even steps / shortens odd ones, step start times accumulate in ms and are
  then converted to frames), so it cannot drift against the note sequencer. `engine_synth_set_clock(bpm, steps, swing,
  running)` (called every UI step, sends only changes) and `engine_synth_motion_restart()` (called when the note sequencer
  starts a run, `seq.fresh`) feed it; the clock is re-sent after every rebuild. Risk: a second copy of the timing rule; if
  `seq.c` changes its swing / step arithmetic, `motion_seq.cpp::schedule()` must follow (a test compares the two for
  3 swings x 3 step counts x 4 tempi). Changing steps / BPM while running changes the phase (no attempt to keep it).
- **Lane rule** (the spec): between *active* steps; STEP holds the previous active step, LINEAR interpolates to the next
  (distances modulo the step count, wrapping); one active step = constant; none (in the first `steps` steps) = the lane
  outputs 0. Steps >= the pattern length are ignored. Output ramps linearly inside a block between the values at its start
  and end (no clicks, 1 block of smear on a hard step).
- **Stopped sequencer = the lanes output 0** (neutral). Bipolar maps 0..100 to -1..+1, unipolar to 0..+1.
- **Targets** are (module, parameter) pairs the mapper realises (`rack_ms_target_ok`: OC Pit / Lvl / PW, FL Cut, SA Drv);
  one `Tgt` row cycles through them. Depth per unit is the ENV table of the mapper.
- **UI**: `MOTION n` page (bars per step for the selected lane, playhead, rows Lane / Step / Val / On) and `MS n LANE`
  (rows Lane / Tgt / Mode / Pol / Dpth next to the lane's curve). Rack view draws a link per lane.

  screen; `audio_samples_rescan` and the Scan row are gone): ADR-041, decisions 51-52.
- **Engine side** (`engine_synth`): `engine_synth_attach_storage(dev)` + `engine_synth_catalog_set()` (C++ header `sample_catalog.h`); the

- **Desktop** (`sample_sim.cpp`): the folder `samples/` (cwd, `..` or `../..`) is the card. `*.smp` join the library; `*.wav` (8/16/24/32-bit PCM

### ADR-031: Envelope curves, hold, start level and the multi-stage Eg (Accepted, `dsp/curve.h`, `modules/synth_modules.cpp`; user choice: both)
Every `Env` segment now has an exact length and a curve (tension): `s(p) = (1 - e^{-kp}) / (1 - e^{-k})`, `k = 8 c`, c in -1..+1 (0 = line,
+ = fast start / slow end like an analog capacitor, - = slow start / fast end). The shape is a 128-interval q15 table built at control time and
read with one interpolation, so a curve costs nothing at run time. New parameters: `hold`, `start` (level the attack starts from) and
`a_curve / d_curve / r_curve`; defaults (55 / 60 / 60 %) are close to the old one-pole feel, but the old asymptotic segments are gone: the attack
reaches 1.0 at its time, the release reaches 0 at its time (tests changed accordingly). The rack shows curves on EN, FL (filter envelope) and the
AMP ENV (new `... CRV` pages). `Eg` is a four-breakpoint envelope (time, level, curve each; time 0 = unused; `sustain` = points played before
holding; own release + curve; `oneshot` ignores the gate so a kick's pitch / amp shape always plays out); rack module `EG` (pages `EG n` editing
the selected point and `EG n REL`). Risks: Env times are now fixed-length (a very short note releases from wherever it is over the full
`release` time); the Eg has only 4 points.

### ADR-032: Modulation depth in real units (Accepted, `core/rack.c rack_depth_*`, `rack_graph.cpp depth_target`; user choice)
A modulator's `Dpth` (and an MS lane's) is a signed value in the unit of its target: **st** for pitch (+-96), **oct** for cutoff (+-8) and drive
(+-4), **%** for level / PW / morph (+-100). Changing the target resets Dpth to a default of the new unit. The mapper turns it into the cable depth
`Dpth / range` and sets the engine node's own modulation range to match (`OSC_PITCH_MOD` / `SMPR_TUNE` 96 st, `FLT_CUT_MOD` 8 oct, new
`SHP_DRIVE_MOD` 4 oct, `OSCX_*` like the oscillator), so a +60 st kick sweep is one setting. Old patches' Dpth values change meaning (the demo
rack's LFO now has 1.5 oct). Modulating resonance / mix / another modulator is still not realised.

### ADR-033: Oscillator engines (Accepted, `modules/osc_engines.*`; user request, inspired by the Plaits idea of macro oscillators)
`OscEngines` (voice scope, type id 60): Karplus-Strong string, modal resonator (harmonic -> bell material), 2-operator FM (stepped ratios), wavefolder,
7-voice supersaw, formant vowel, 12-harmonic additive and "dust" (random impulses ringing a pitched resonator). Every engine has the same three
controls: pitch, timbre, morph (named by effect, see the table in the header); in 1 is the gate that strikes the string / modes. In the rack the
OC `Wav` list continues with the engines (value >= `OC_FIRST_ENGINE`): PW is shown as `Timb`, a `Mrph` row appears, and timbre / morph are
modulation targets (an engine has four: Pit Lvl Timb Mrph). The mapper builds `T_OSCX` instead of `T_OSC` for them, so changing the wave class is a
rebuild. Costs: KS 4 KB per voice; aliasing is naive like the shaper (ADR-013); the preview in the graph box is a sketch, not the signal.

### ADR-034: Saturation modes, the FX rack and the new effects (Accepted, `modules/fx2_modules.*`, `core/fxrack.*`; user choices: all families, flexible rack of 4)
- **Shaper** modes (also SA in the rack): Tanh, Clip, Fold, Crush, **Tube** (biased tanh, even harmonics), **Tape** (tanh + gentle high cut), **Diode**
  (asymmetric), **Cheb** (T3 + T5), **Rect** (full-wave: octave up), **Decim** (sample-rate reduction); asymmetric ones through a DC blocker.
- **Effects** (global, stereo): Phaser (2..8 all-pass stages), Flanger, Tremolo / Auto-pan, Compressor (linked peak detector, log-domain gain, makeup, parallel
  mix), 3-band EQ (RBJ shelves + peak; biquads with Q32 coefficients and a 12-bit-extended feedback: rounding the output inside the loop destroyed the low
  shelf at 96 kHz), Ring modulator / frequency shifter (Niemitalo all-pass Hilbert pair), **Convolver** (direct form, up to 512 taps, 8 built-in
  impulse responses generated from filter models: 1x12, 4x12, bright, dark cabinets, acoustic body, violin body, drum shell, telephone; a custom IR can be
  loaded in chunks of 120 taps with `set_blob`), and **Comb** (voice scope tuned resonator following the key, optional second comb at an interval; rack
  module `RS`).
- **FX rack** (menu tab FX RACK, replaces the CHORUS+DELAY and REVERB tabs): four master slots in series, each any of Drive, Chorus, Phaser, Flanger,
  Trem/Pan, Comp, EQ, Shift, Delay, Reverb, Cab (or empty), four parameters per type (`fxr_*` descriptor table: ints in screen units). Changing a slot's
  type rebuilds the master chain, parameters are live messages. Master nodes are `RN_FX + 2 * slot`. `kMaxNodes` 48, `kMaxEdges` 160, `Registry::kMax` 128.
  Defaults: chorus (off), delay (dry), reverb (dry), empty (audibly neutral like before).
- Risks: the convolver costs `taps x 2` MACs per sample (a 256-tap cab is about 25 MMAC/s: measure on the S3); the compressor and the shifter are not
  measured against a reference beyond the tests; IRs from the card are possible through the chunk API but not wired to the library yet.
- **Convolver on the S3 (2026-10-09, user request: "unusable from the start, make it run at 128")**. Measured before: 25 cycles per tap per frame
  (a wrap mask, two 16-bit multiplies and two 64-bit adds per tap, 23 instructions): 64 taps 52k, 128 taps 100k (57 %), 256 taps ~195k cycles per
  32-frame block (112 %, 400-570 DMA underruns per second). The IR was also regenerated in **double** on the audio thread (soft float on the S3, 4 KB
  of stack) on every IR / Length change. Exact rework (user choice "PIE kernel + IR off the audio thread"): linear history written at an advancing
  position (moved once per kRun / frames blocks: a move per block cost ~30k cycles with the buffers in PSRAM), taps reversed in 8 shifted copies so
  every 128-bit load is aligned, the dot products in `pie_conv2_s16` (`fft_s3.S`, `ee.vmulas.s16.accx`, 40-bit exact; serial `pieconv`: 0 of 768
  sums differ from C, 161 cycles for 128 taps x 2 channels) and the same layout in C on the host (`convolver_is_bit_identical_to_a_direct_convolution`).
  The IR is computed by engine_synth on the control thread (`conv_builtin_ir`) only when IR / Length change, sent as `ConvBlob` chunks; the module
  switches IR and length together on the last chunk (rebuilding its 8 copies, ~10k cycles estimated, not measured). Measured after (cycles per block):
  **64 taps 7.9k, 128 taps 10.0k, 256 taps 14.2k, 512 taps 22.3k**, 0 underruns; about 5.8k fixed + 32 per tap. Memory: ~14 KB per Convolver (was
  5 KB), in the fast heap, which is in PSRAM on the board at the moment (see CONTINUE.md, internal RAM).

### ADR-022 addendum: ring slots are chosen by the loader, the overview lives in the header (Accepted; found on the board)

- **Bug:** a block always sat in ring slot `block % 8`. A loop's end blocks (e - 2 .. e) and start blocks (s - 1 .. s + 3) are both wanted around the wrap, and when they share residues mod 8 the loop start could not be prefetched: every lap
  dropped out (a hold-and-decay underrun at the loop point). The demo pad (28800..96000 = blocks 14..46) is such a loop; the existing loop test happened to avoid it.
  Test `a_long_loop_wraps_without_underruns_wherever_its_blocks_fall_in_the_ring` (four alignments, 3 laps, values checked at both wraps) failed with an underrun per lap and passes now.
- **Fix:** the loader puts a block in any slot that is not in flight and does not hold a still-wanted block (empty and stale ones first); the audio thread finds a block by scanning the 8 slot tags (a handful of atomic loads once per block, only when the
  cached block runs out). The set of wanted blocks (<= 8) is unchanged, so the ring size is too. Cost: none measurable on the host.
- **`.smp` header:** bytes 100..163 now hold the 64-bucket amplitude overview the sample list draws. Old files have zeros there and are still read (the reader computes the overview: 64 card reads per file at scan time on the board, so re-cook them).
- **Loader API:** `engine_synth_io_pump()` returns whether reads are still in flight; the I/O task keeps going (up to 8 rounds) instead of sleeping a tick after every pair of reads. `engine_synth_sampler_stats()` exposes the underrun and block-read counters.

### ADR-022 addendum 2: high pitch, starved voices and the 64-bit atomics (Accepted; measured on the board 2026-10-05/06)

- **Symptom:** high sampler notes stuttered the whole synth. The stream speed is proportional to pitch (one voice at 8x its root reads ~700 KB/s at 44.1 kHz), the card
  (SL32G, SPI) gave ~640 KB/s, and a starved voice cost ~20x its CPU: **182k cycles per block for one voice** (budget 174k).
- **Cause:** a 64-bit `std::atomic` load is a locked libatomic call on the ESP32-S3. The Sampler's `fetch()` searched the ring tags on every miss, 4 times per sample (Hermite);
  the loader's `issue_streams()` re-read every slot tag for every wanted block of every stream (thousands per issued read with 6 voices, on the card task's core).
- **Fixes (all exact; output checksums identical with `SC_SAMPLER_NO_FAST`):** (1) `miss_blk_`: a missing ring block is searched once per `process()` call (C7: 182k -> 27.7k cycles,
  0 blocks over budget); (2) `issue_streams()` reads each stream's tags once per pass (3 voices at C5..G5: 487 -> 633 KB/s, underruns ~150 -> 0 per 2 s);
  (3) `starved_block()`: a block whose playhead stays inside a missing ring block outputs the held-value decay directly (6 starved voices: render 1444 -> 966 us, blocks over budget 325 -> 7);
  (4) `ENGINE_RING_BLOCKS` 8 -> 12 (48 KB of bulk RAM per stream, 7 blocks ahead): at 8x a block lasts 5.3 ms and a slow card read 22 ms, 3 blocks ahead underran.
- **Rule:** never read a 64-bit atomic in a per-sample or per-candidate loop on the S3; copy it once.
- **Limit left:** the card. At 25 MHz (in spec: this card has no high-speed mode, CMD6 group 1 = 8001) one voice plays clean to 8x, and the voices' speeds add up to ~600-650 KB/s
  (e.g. 3 notes at C5..G5 of a C4 sample). A 4 KB read takes 4.0 ms raw, ~6 ms in practice with several voices (the card's own latency spikes, 5-9 ms). Options (user decision, see CONTINUE.md).

### ADR-030 addendum: .wav / .mp3 are listed at once and converted when assigned
The library lists `.wav` and `.mp3` next to `.smp` (entry marked with `*`, `pending`, the graph says "converts on assign"). The decode (24-bit / float / any channel

### ADR-035: Running on the ESP32-S3: measurements, rules and the decisions taken (Accepted; measured on the first prototype; the user took every quality trade)

First hardware runs (board "HWV1", see DEVELOPING.md). Budget: **160000 cycles per 32-frame block** (240 MHz, 48 kHz). The default patch started at 1 voice with reverb and delay;
after the work below the 4-engine startup patch (`rack_init_startup`: Karplus, Modal, Supersaw, Additive into one filter, delay 1000 ms / 40 %, reverb 40 %) runs 4 voices inside the budget. How the work was
done (measure on the board with `tools/serial_test.py`, then change, then re-measure) is the skill `.claude/skills/esp32-optimize`.

**What this core costs** (cycles, measured by `HWV1_BENCH`, in-order single-issue, 240 MHz):

| Operation | Cycles | | Operation | Cycles |
|---|---|---|---|---|
| int32 multiply + shift | 3 | | float add | 4 |
| int32 x int32 -> int64 >> 16 | 13 | | float multiply-add (dependent chain) | 6 |
| int64 x int64 >> 16 | 24 | | int -> float / float -> int | 4 / 8 |
| high-word multiply `mulh()` | 5 | | **float divide** | **68-72** |
| table read, internal RAM | 5 | | **float <-> int bit cast (memcpy)** | **62** |
| table read, flash, cache miss | ~120 | | 64-bit divide | library call, 100+ |
| Hermite 4-point read (RAM / PSRAM) | 64 / 70 | | linear read (RAM / PSRAM) | 18 / 20 |
| SVF tick, fixed point with saturation | 202 | | SVF tick, float32 (FPU) | 25 |
| 2-section filter sample, integer coefficients + convert / float batch | 322 / 342 | | `pitch_to_inc` / `svf_g` / `svf_coef` | 21 / 14 / 54 |

Rules that follow (each one cost a wrong turn to learn): the FPU wins on a **chain of multiply-adds on state** and loses on conversions, division, bit tricks and indexed memory access; dependency latency
(4-6 cycles per float op) dominates short loops; 64-bit arithmetic in the audio path is expensive (use int32 and `mulh`); cycles are about the instruction count on this core, so read the disassembly when numbers do not add up.

**Decisions and mechanisms:**

1. **Compiler**: the Arduino framework puts `-Os` after the project's `-O2`; `build_src_flags = -O2 -fno-stack-protector` fixes the engine's inlining. `SC_HOT` (= `IRAM_ATTR`) marks every module `process()`
   (flash code runs through a 16 KB cache shared with the display core); `SC_TABLE` (= `DRAM_ATTR`) keeps the lookup tables in internal RAM.
2. **Float exception to guideline 2** (user decision): the filter tick (`svf_tick_f`) and the vowel / dust filters use float32 on the FPU (202 -> 25 cycles). Coefficients stay integer (`svf_coef`), converted by `svf_to_float`.
   When the cutoff modulation is a straight line over the block (checked at 3 points, tolerance 6/256 semitone) the coefficients are computed at both ends of the block and interpolated per sample (no stepping);
   anything else (audio-rate FM of the cutoff, sample and hold) keeps the exact per-sample computation. `ENGINE_FILTER_EXACT=1` forces exact. 11.4k -> 4.4k cycles per voice.
3. **Bypass of idle effects**: Chorus mode off, Delay mix 0 and Reverb mix 0 copy the input (state cleared once on entering bypass). -40k cycles at idle.
4. **Delay-line primitives**: `lerp15` uses a 15-bit fraction (the 16-bit one overflowed int32 when neighbours differed by more than 32768); `read_lerp` / `read_hermite` have a one-wrap-check fast path; the one-pole low-pass,
   `mul31` and the DC blocker use `mulh` (`mul31` now floors); `mul15n` skips the saturation when the gain is below 1.
5. **Reverb** (user choices): `ENGINE_REVERB_HALF=1` runs the Dattorro tank at 24 kHz (half-band FIR -1 9 16 9 -1 / 32 down, cubic midpoint up; delays defined in seconds so decay and size are unchanged; combined response about
   -3 dB at 8 kHz, -6 dB at 10 kHz, -12 dB at 12 kHz): 38k -> 20.5k cycles and 91 -> 49 KB of internal RAM. `ENGINE_FX_MONO=1` computes one channel in the delay (one line, half the cost, -192 KB PSRAM) and the left taps only in the
   reverb. Both are build flags, on in the prototype's `platformio.ini`; the stereo-specific tests fail with MONO on by design.
6. **Memory** (internal RAM for the engine is the "fast heap", about 106 KB): when it is full, allocations **spill** to PSRAM (`Heap::set_spill`) and everything touching them gets slower (a mixer went from 88 to ~20 cycles per sample once
   the oscillators stopped taking the space). Oscillator engine tables are shared (`Tabs`), the Karplus string buffers (4 KB x 32 instances) live in the bulk heap, the command ring is 128 entries. `[HEAP]` reports used / spilled bytes.
7. **Oscillator engines**: the per-block setup is cached on (engine, pitch step, timbre, morph); a **fast path** runs a tight loop per engine when the pitch is steady and the gate does not change inside the block (the loop around the
   engines was about 50 cycles per sample); modal modes are decaying phasors with the rotation normalised to unit length (exact decay time, tested); additive uses the Chebyshev recurrence (everything outside the 12 harmonics is -72 dB);
   the supersaw has 5 saws (the outer spread kept at +-4.5 %, side level x 6/4); Mix4 skips zero-gain inputs. Per oscillator and voice, cycles per sample, before -> after the engine work: add 509 -> 263, modal 503 -> 229, ssaw 348 -> 237, vowel 240 -> 217, karp 131 -> 117 (string buffer now in PSRAM), fm2 134, fold 115 -> 117, dust 142 -> 141.
8. **A knob must never change the graph's shape.** Adding or removing a node or cable, or making a cable exactly unity (a unity cable is wired straight through, with no gain stage), is a full `Engine::load` = an audio stall of 85-250 ms. Cable
   depth is now a live command (`Engine::set_edge_depth`, `Cmd::SetDepth`); modulation cables are capped at 32766; the filter's own envelope node always exists (amount 0 = gain 0). Test: `changing_a_modulation_depth_does_not_rebuild_the_graph`.
9. **Dev tooling** (all removable, see the flag list in DEVELOPING.md): `[AUDIO]` render time and graph build count, `[PROF]` per module, `[SEC]` stage timers in Reverb / Delay, `[OSC]` per engine, `[HEAP]`, `[BENCH]`, and a serial command channel
   (`DEV_SERIAL_CMD`: `on`, `off`, `chord K`, `eng a b c d`, `release`) driven by `tools/serial_test.py`.

Risks accepted: float and fixed point now coexist in the filter (two representations to keep consistent); the supersaw is thinner than the 7-saw version; the half-rate reverb is darker in the top octave; mono FX lose stereo width;
the interpolated filter coefficients are a (tested, small) approximation for fast but smooth modulation. Items not yet done are listed in CONTINUE.md ("Next performance steps").

### ADR-036: Voice modes (Mono / Paraphonic / Poly), capture, cost metadata (Accepted, staged; user choices of 2026-10, stage 1 in progress)

**Why.** The GENERAL tab's "Voices" was cosmetic: `Engine::init` allocated 8 copies of every voice module and nothing applied `cfg.voices`. A patch could not trade voices for budget, and a polyphonic modular patch costs 24k cycles per voice (ADR-035), so 4 voices is its ceiling.
The user wants a modular engine whose budget is knowable (a DSP "point" system later), a usable synth with less patching, and a way to get polyphonic sounds out of a rich patch.

**Decisions taken by the user** (options and their trade-offs were offered; recorded, not to be re-litigated):
1. **Three modular modes.** *Mono* (one real voice, the whole budget for one patch), *Paraphonic* (several voices share one filter and its envelope) and the existing *Poly* kept as a legacy third mode (N real voices, copy of every module per voice). Nothing is removed.
2. **"Internal resampling" means capture, not real-time polyphony.** The audio of a (mono or paraphonic) modular patch can be recorded into a sample that the Sampler module then plays, chops, loops and pitches in another part of the workflow. (Rejected: pitched real-time playback of the patch's own output; a half-rate voice.) Polyphony of a captured sound comes from the Sampler.
3. **Paraphonic structure.** A rack is split at its first filter: the modules before it (several oscillators, saturations, audio-rate FM / modulation between them) run per voice; the filter, its envelope and everything after it (post-filter chain: saturation, VCA, ...) run once for all voices. The envelope behaviour is selectable: first-key retrigger (legato gate for added keys), retrigger on every key, or a per-voice amp envelope in front of the shared filter.
4. **DSP budget.** This round only adds *cost metadata* (a cost model per module type, calibrated from the board's `[PROF]` numbers, and a host/board check). The points meter and the refuse/warn logic in the RACK tab come later.
5. **The voice mode is part of the synth type** (user, after hearing stage 1 on the board): GENERAL's Type lists *Modular*, *Mod Mono*, *FM*, *FM Mono*; there is no separate Mode row. The Mono types (rack or DX7) have Glide and Legato; the polyphonic ones have Voices. Paraphonic will be another type (e.g. *Mod Para*).

| 5 | Modular engine optimization with the measure loop (`esp32-optimize`): per-voice Filter 4.8k, Env 2.3k, oscillator engines, VoiceOut | alongside |

**Stage 2 as built (2026-10-06).** `ProcessCtx` carries the voice array and the held-key count. Per voice: NoteIn, the sources and every processor before the first
filter (sources placed after it join the voice part, so they also go through the shared filter), then `ParaGate` (a released key is muted in 5 ms while other keys
are held; the keys of the last chord keep sounding through the shared release) or, with PEnv = Voice, the AMP ENV per voice; VoiceOut (tail = amp release + 400 ms).
Shared, after `BusIn` (left: the voices are centred): the filter (`Filter_G`) with its envelope (`EnvG` gated by `GateIn`), the processors after it (`Shaper_G`), the
shared amp (`EnvG` + `Vca_G`, unless PEnv = Voice), then the FX rack. No filter in the rack: only the amp is shared. Limits: a Resonator (Comb) after the split is
dropped (it follows the key); an EG or an oscillator aimed at a shared module is not realised (no global EG yet; a voice cannot feed the shared chain); the shared
chain is mono until the FX rack. The voice part's Mix4 chain (about 2k cycles per voice at 8 oscillators, 32 frames) was replaced on 2026-10-06 by cables into one MIX step (ADR-026): on the board, 44.1 kHz / 64 frames, Para 8 osc x 4 voices, 4 keys 82.6k -> 66.4k cycles; 4 osc x 8 voices, 8 keys 100.5k -> 72.0k.

**Risks accepted / known:** a voice-count or mode change rebuilds the voice modules (a short audio stall and a reset of their state, once per change); mono glide runs at block rate (0.7 ms steps, exponential); the paraphonic split makes modulators that feed the shared half global-scope (a per-voice LFO cannot modulate the shared filter: it is a different LFO, not a mix of the voice ones); a captured sound is a snapshot (no later parameter changes).

### ADR-037: "Strings", a third synth type with 32 voices for pads and big chords (Accepted; user choices of 2026-10-06; built and host-tested, not on the board yet)

**Why.** The ESP32Synth library (tried on the board as a second engine, `alt_esp32synth.cpp`) gets its 80 voices from very thin voices: one oscillator x a linear envelope, no filter. The user wants that idea as
a purpose-built engine of our own for lush pads and many-voice instruments, and the library removed from the project at the end.

**Decisions taken by the user** (options with pros and cons were offered; recorded, not to be re-litigated):
1. **A per-voice module in our graph**, like FM: `NoteIn -> Strings -> VoiceOut` per voice, the shared chain after the voices. The engine's voice ceiling goes from 8 to 32 (`ENGINE_MAX_VOICES`).
   (Rejected: one global "bank" module with its own allocator, cheaper but outside the voice manager.)
2. **Two detuned oscillators per voice** (saw / pulse / triangle, detune, level of the second) and a linear ADSR computed once per block (ESP32Synth's envelope).
3. **Both oscillator kinds, switchable**, so the user can judge sound against CPU / RAM: a naive phase accumulator (cheapest, aliases) and band-limited mipmap tables (one table per octave band).
4. **After the voices:** a shared filter (Strings type only, stereo) and a new string **Ensemble** effect (FX rack, any synth type). **Per voice:** a one-pole lowpass that can be switched off, its cutoff following the voice's envelope and the key.

5. **In the modular rack too (user, 2026-10-06, "Both"):** an oscillator engine *Strng* (OSC Wav list: a detuned pair, Timbre = detune up to 50 cents, Morph = saw / pulse / tri
   in thirds) and a quality row *Q* on the OSC TUNE page: Blep (PolyBLEP, as before) / Mip / Naive for Saw, Pulse and Tri (and Naive / Mip for Strng). One table oscillator
   (`wt_osc` in `dsp/wavetables.h`) serves the Strings voice, the Strng engine and the plain waves.

**Risks / known:** mipmap tables switch band per octave (a small timbre step, no crossfade); the tables are read from flash (a cache miss costs ~120 cycles) unless copied to RAM;
the envelope is linear (as the library's); the Strng engine follows the pitch at block rate. The 32-voice ceiling: the plan and instance-record tables are now sized by the
real voice count (heap), so the ceiling costs almost nothing. Measured on the board (`dump` of the engine output, C5, dry): saw Mip -40.6 dB / Naive -18.4 dB of
inharmonic power, pulse -40.2 / -20.1, triangle -39.7 / -39.7, identical to the host.

### ADR-038: Light filter types, a 32-bit voice bus, the knob glide (Accepted; user choices of 2026-10-06; measured on the board, NOT listened to)

**Context.** The user asked for a lighter filter, a cheaper voice sum, and a fix for the latency / steps when moving the cutoff.

**Decisions (the user's).**
1. Three new FL types, opt-in (the default patches keep theirs): **LP6** (one-pole, 6 dB/oct), **Ladr** (four one-poles + resonance feedback + cubic soft clip, 24 dB/oct, Moog-like,
   not zero-delay), **ChLP** (Chamberlin state-variable LP, cutoff stops at about fs / 6). They are an `algo` parameter of the existing Filter module, so a type change is a live
   parameter, not a rebuild. Float (the integer Chamberlin would overflow at high Q without 64-bit products); one coefficient per block end, interpolated: no exact per-sample path
   for audio-rate cutoff FM. Res (Q 0.5..10) maps to 0..1: Ladr feedback 3.9 x res (output x (1 + 0.5 k)), ChLP Q directly.
2. The voice bus is 32 bits: VoiceOut adds without clipping, BusIn saturates once (before: a q15 bus clipped after every voice). Changes the sound only when the voice sum clipped.
3. The cutoff knob glides with a ~20 ms one-pole (was a quarter step per block, 2-5 ms), and the coefficients follow it across the block.

**Measured** (board, 44.1 kHz / 64 frames, startup patch in Poly, 4 voices, Filter cycles per block): LP 18.0k, LP24 24.7k, **LP6 7.8k, ChLP 6.4k, Ladr 15.9k**.
VoiceOut with the 32-bit bus: 6331 -> 4213 for 8 voices (Para 4 x 8, 8 keys; whole block 71.5k -> 69.4k). Host: responses against theory (LP6 -3.0 dB at the cutoff,
Ladr -49 dB two octaves up, ChLP Q 10 = +20 dB), bounded at full resonance with the cutoff at its top.

**Found on the way (exact fixes, measured):** a voice start cleared every OscEngines' 4 KB Karplus buffer in PSRAM whatever the engine (about 1.5 ms of the block per note-on:
an audio dropout on every played note); now only the strike clears it. The UI loop waited ~120 ms for each full-frame I2C redraw, so notes, LEDs and knob moves arrived late
(DEVELOPING.md, `display_esp32.cpp`).

### ADR-040: Rack lanes, Sum points and FX modules in the rack (**Superseded by ADR-041** on 2026-10-09; stage 1 code of 2026-10-08 to be reworked, not extended)

Stages: (1) model + rules + editor (lane per slot, Sum, FX modules, placement rules, 16 slots, the 3-row rack strip), host UI tests; (2) engine (buses,

### ADR-041: Two branches + row M, a Para switch, Synth and Pads sections (Accepted; user choices of 2026-10-09; phases 1 and 2 built 2026-10-09)
**Why.** The user's real need behind ADR-040 was (osc 1 -> filter 1) + (osc 2 -> filter 2), each filter per voice or paraphonic, plus a sampling and
production loop (synth -> capture -> pads). Three lanes with Sum modules were more than that and made the scope of every module hard to read.
The remaining phases and open questions: CONTINUE.md "Next: the production workflow"; the user's brief with screen sketches: https://claude.ai/artifact/HiSWqALbydqwbo8ibHp8nA.

**Decisions taken by the user** (recorded, not to be re-litigated):
1. **No lanes in the engine, no Sum module.** Rows exist only on the RACK page; there are no separate note streams.
2. **Rows 1 and 2 are two parallel branches**: same notes, same voices, summed at the output. **Row M** is a chain on the sum of both branches,
   always shared (once, not per voice). Oscillators side by side in a branch are summed, as today.
3. **Para is a switch on any processor**: from that module on, the branch runs once on the sum of its voices. Heavy FX (Delay, Reverb, Chorus,
   Spectral, Cab, Ensemble) always run shared, so a branch becomes shared at the first of them. One way only: a shared module never feeds a

5. **One synth plus a separate Pads section** (SP-404 style); two workflows, the user works in one or the other. A pad = a sample per key with

6. **Step sequencer for the synth** (notes on the grid, MIDI input recorded into it); **capture** by a global shortcut from any page, modes manual /
   threshold / N bars on the grid / auto-sampler; capturing a sequenced pattern gives an on-grid sample, a live capture is not quantized.
7. **Clock**: internal, MIDI clock in and out. **One settings page** (LEDs, keys, clock, MIDI) reachable from both sections.
8. **No saved data to keep**: no sound design exists yet; old patches are deleted and file formats change freely, no migration code.

**Engine sketch** (phase 2): the voice bus carries both branches; each branch's Para point (explicit, or the first heavy FX) sums its voices into a
shared chain; the two branch outputs mix, then row M, then the output. The ADR-040 per-voice FX (`<Scope>` templates of Trem, EQ, Ring / Shift,

**Sample tools step 4, Time & pitch, as built (2026-10-10; 204 engine tests in the 6 configurations, 93 UI tests, simulator + firmware

- Five EDIT operations: **Stretch** (25..400 % of the length, the pitch kept), **Pitch** (+-24 semitones, a semitone per step, a cent
  with fine; the length kept), **Speed** (25..400 %: the length and the pitch change together, like a tape), **Fit beats** (the pitch
  kept) and **Fit speed** (by the speed): the pad's loop, or Start..End when it does not loop, is made to last N beats (1..128) at the
  clock's tempo; the amount row shows the length factor ("8b x1.07"); beyond x0.25..x4 it is refused. A neutral amount (100 %, 0 cents,

- **The whole file is processed with one factor**, and the pad's Start / End / LStr are scaled with it (`render_adopt`), so the
  lead-in before a loop stretches along and Sync still puts the loop start on the grid. Loop points and slices in the file's header
  scale too.
- Engine (`engine/offline/process.*`, ProcOp `Stretch`, `Resample`, `Pitch`; amounts: the new length in ppm, cents):
  - Stretch = **WSOLA** in the time domain: Hann windows of ~43 ms (hop 1024 at 48 kHz, scaled with the file's rate) overlap-added at
    50 %; each window is taken within +-10.7 ms of its ideal place, where it continues the previous one best (normalised
    correlation over the overlap, on every 4th frame and every 4th offset, then refined to the frame; when going straight on is
    within reach it is taken: x1 gives the file back, +-1 LSB). The first window does not fade in: the attack is the file's own.
  - Resample = a 32-tap Hann-windowed sinc, 32 phases interpolated, the cutoff lowered to the new Nyquist when the result is shorter.
  - Pitch = Stretch by the pitch ratio feeding the resampler, in one pass.
  - Measured (tests, a pure tone at -6 dB): the level stays within 0.01 dB; a stretch's seams are 34..47 dB under the tone
    (whole-frame alignment), a pitch shift's 36..52 dB; resampling leaves 63 dB or better, 15 kHz slowed to 10 kHz loses 0.00 dB,
    and a tone that would fold over on a x2 speed-up is at -44 dB.
- **My choice, open to the user (decision 36 names "WSOLA / phase vocoder"): only WSOLA is built.** It is the right tool for drums and
  loops (transients stay sharp up to about +-30 %; further out a hit can double or smear) and it is weaker on sustained chords and
  pads (a faint flutter at the window rate). A phase vocoder is the opposite (smooth on sustained sounds, soft on drums); it needs a
  float FFT of 2048+ points, ~30 KB of working memory out of the ~59 KB of PSRAM the board has to spare. Paulstretch (the Texture
  group) needs the same FFT, so a "Tonal" stretch mode is cheap to add with that step if the user wants it.

- **Engine**: the Pads player has four stereo buses (8 outputs; `kMaxOut` 4 -> 8); `pads_graph_build` (rack_graph.cpp) wires
  Pads -> the chains in the routing's order -> MasterOut, with the rack's own module mapping (`fx_params`, a filter / saturator as a
  node per channel). An empty chain passes its input on. `engine_synth_pads_fx`: the same shape = only the values that moved are sent
  (a knob never reloads the graph); another shape (a module, the routing) = a reload, through which the pads keep playing and the
  untouched effects keep their tails (instances are kept by id and type; the chains' nodes are 300 + 2 x the module's id).
- **UI**: **Menu in the Pads section opens the FX page** = the RACK page (scr_rack.c) on that rack: rows A / B / C, a push on a cell
  opens its menu (Edit, Type, Insert, Row, Delete; Type only offers what a chain takes); **the header is the routing** (left / right
  on it) with the load next to it. **Edit** opens the module's values (a list and the effect's sketch); there the four column knobs
  drive its first four values. Back: values -> chains -> pads.
- **On the board** (`tools/padsfx_test.py`, serial `pad fx`; 8 looping pads into chain A, 48 kHz, cycles per 32-frame block of
  174 000):

  | chains | cycles | load | dropouts |
  |---|---|---|---|
  | none | 41 200 | 24 % | 0 |
  | filter + saturator | 53 000 | 30 % | 0 |
  | delay + reverb | 75 300 | 43 % | 0 |
  | EQ, compressor, delay, reverb | 114 200 | 66 % | 0 |
  | 12 light ones (4 a chain, A+B+C) | 208 800 | 120 % | 520..700 per run |
  | delay, reverb, chorus in each chain (9) | 192 700 | 111 % | 360..470 |

  Per module (stereo): saturator 3.7 k, tremolo 4.5 k, ring / shift 5.0 k, filter 8.3 k, compressor 8.7 k, delay 8.8 k, chorus
  12.9 k, cab 15.6 k, flanger 15.9 k, ensemble 17.8 k, spectral 19.3 k, phaser 19.5 k, reverb 26 k, **EQ 26.5 k** (as much as the
  reverb for three bands; fixed the same day: 5.9 k, see "Speed" below); the 8 pad voices 40..48 k.
  **So decision 47's risk is real: four to six effects fit next to 8 pads, twelve never do.** Nothing is refused; the FX page's
  header shows the load estimated from these costs with all 8 pads sounding ("FX A+B/C 66%", a "!" from 90 %).
- Static RAM: the chains cost 2 KB (the rack in `pads_t`); loading pads.cfg and the serial `pad def` no longer keep a spare copy of

- Not built yet: the live synth's entry into the chains (step 4), modulators on an effect's values, a per-chain level or on / off,

**Capture / resampling, design (user, 2026-10-11; options offered):**
50. **Capture next** (before the live synth and song mode; my recommendation, taken), and **it records the whole Pads output** (all
   pads, all chains; "from a Record key until Stop or for a set number of bars on the clock").
- My choices inside that, open to the user: a **Rec** key on the Pads layout's free key (right block, row 2, between Mute and Stop;
  a key function, so it can move); the recording goes to **the selected pad when it is empty, else to the next empty one**; it starts
  at the **first sound** (about -50 dB), or with a length on the **next bar line** of the running clock; **Shift + Rec** sets the
  length (until Rec again / 1 / 2 / 4 / 8 bars at the tempo); a recording with a length becomes a pad that **loops on the bar**;
  the pad plays it at **full level** (a copy of a copy must not fade); files are named rec1, rec2 ...
- **Mono**: the library's samples are mono, so the recording is (L + R) / 2: a ping-pong delay or a wide reverb folds to the middle.
  Stereo samples would be a format change through the whole sampler (to decide separately).

**Capture as built (2026-10-11; 216 engine tests in the 6 configurations, 100 UI tests, simulator + firmware built, RAM 65.7 %;
flashed and measured by me; NOT tried by the user, NOT listened to):**
- **The tap** `engine/sampler/capture.*`: MasterOut hands it every block it receives, before the volume (the volume knob and the
  metronome do not reach the recording); it mixes to mono into a ring (16384 frames, 0.37 s) that the card thread empties. Armed, it
  waits for the bar line (to the sample) or for a block over the threshold; with a limit it stops after exactly that many frames.
  What does not fit in the ring is counted as lost.
- **The card job** `platform/engine/capture_job.cpp` (`engine_synth_capture_start / stop / poll / done / step`, HAL
  `audio_capture_*`): 8 KB at a time into `<name>.smp.tmp`, the overview kept while the length is unknown (64 windows that merge in
  pairs when they are full), the header last, then the rename. Its memory (41 KB of PSRAM) only while it runs; not together with a
  processing job. The card task writes a recording's chunk first on every round.
- **The app** (`capture_key`, `capture_poll`): arms, stops, finds the file in the library, puts it on its pad and selects it. The
  grid's header shows "REC ready" / "REC 0:07"; the Rec key is dim, blinks while armed, is lit while it records. A recording ends
  when the section is left; one without a length stops by itself after 5 minutes.
- **SD driver: multi-block writes (CMD25 with ACMD23)** for runs of sectors, single blocks as before: it was the precondition (a
  recording needs 88 KB/s sustained) and it speeds the sample jobs up by 15..30 % (Reverse of 1.5 s: 1.8 -> 1.3 s; Normalize 2.3 ->
  1.8 s; Paulstretch x4 12.1 -> 10.3 s). Checked with a read-back of every write (serial `pad verify 1`): 1922 sectors, none differed.
- **On the board** (`tools/capture_test.py`, serial `pad rec`; 6 s each, 264 600 frames at 44.1 kHz): silence, 8 pads in memory,
  the same through delay + reverb, 1 / 2 / 4 streamed pads: **0 frames lost, 0 stream underruns in every case**.
- Not built: capture in the Synth section (the tap is there: MasterOut feeds it in both), threshold / pre-roll settings, a count-in,
  choosing the destination pad by hand, overdub.

**Speed: the EQ and the sample jobs (2026-10-11, while the user tests; 218 engine tests in the 6 configurations, 100 UI tests,
simulator + firmware built, RAM 65.8 %; flashed and measured by me; the sound is meant to be unchanged: see each check):**
- **EQ: 26.5 k -> 5.9 k cycles a block** (stereo). Its three sections were int64 biquads with Q32 coefficients (five 64-bit
  multiplies a tick, ~140 cycles on the S3); they run in float32 now, a channel from one conversion to the next. The high shelf
  (6 kHz) is the same biquad in float. The low shelf (150 Hz) and the peak (down to 65 Hz) are the same transfer functions as a
  trapezoidal state-variable filter (the cookbook prototypes as 1 + m1 BP + m2 LP): a float32 direct form loses its accuracy near
  z = 1 (measured: 6.7 LSB rms on a 30 Hz tone through the shelf, against 0.8 for this form). Checked against the same filters in
  double precision (`eq3_matches_its_cookbook_sections_in_double_precision`): **0.3 .. 0.8 LSB rms, where the int64 loop was off by
  1.0 .. 2.6** (it rounded to 16 bits after every section). `ENGINE_EQ_EXACT=1` keeps the old loop.
  On the board: EQ + compressor + delay + reverb 66 % -> 53 %; twelve light effects 120 % with dropouts -> 81 % without.
- **Sample jobs**, a profile first (`ENGINE_PROFILE`: the stages of a spectral frame, printed by the serial `pad edit`): of a frame's
  58 ms, 35 went to **reading its whole 4096-frame window from the card again**, 4..5 to each FFT. Four exact changes, each checked
  by a fingerprint of the output (`offline_time_ops_fingerprint_and_source_reads`: the same 8 numbers before and after):
  1. the window is **kept between frames** and only its new end is read (`Processor::slide`; WSOLA's search range too): the source
     is read once instead of 4 to 8 times;
  2. the job's file reader keeps **one block** and asks the card for whole aligned blocks (a small unaligned request cost three
     card commands, ~12 ms);
  3. a spectral operation's **frame and sine table lie in internal RAM** while the job runs (20.5 KB, plus the reader's 4 KB), when
     there is room: a pass over a block in PSRAM costs milliseconds. Without it the job runs as before, in PSRAM (the same result).
     It also frees PSRAM: Tonal pitch got the kept window too (it had no room for it), and the largest job borrows 37 KB of PSRAM
     instead of 48.5;
  4. no `lround` in the per-sample loops (a library call on the S3), one cos / sin per spectral region instead of per bin, one
     power per bin in the peak search instead of five.

  | operation (a 1.5 s sample) | 2026-10-11 first | after CMD25 | now |
  |---|---|---|---|
  | Normalize | 2.3 s | 1.8 s | 1.9 s |
  | Reverse | 1.8 s | 1.3 s | 1.35 s |
  | Speed 200 % | 1.5 s | 1.3 s | 1.1 s |
  | Stretch 150 % (Beat) | 4.6 s | 4.4 s | 2.8 s |
  | Pitch +7 (Beat) | 4.8 s | 4.6 s | 2.8 s |
  | Stretch 150 % (Tonal) | 8.0 s | 8.1 s | 4.4 s |
  | Pitch +7 (Tonal) | 8.1 s | 8.1 s | 4.4 s |
  | Paulstretch x4 (6 s) | 12.1 s | 10.3 s | 6.1 s |

  A Tonal stretch while 4 pads stream: 16.2 s -> 9.6 s, still no stream underrun. A spectral frame is 23 ms now (load 8, FFT 4,
  spectrum 5, inverse FFT 4, overlap-add 2); what is left is mostly the card's write rate (~150 KB/s).

**The sample library read on demand, and a browser (user, 2026-10-11: "there is only 32 samples available, it needs a real browser";
both choices were my recommendation):**
51. **Folders, read on demand.** The library is everything below `system/samples`, in folders of any depth. Nothing is scanned at start:
   a folder is read when the browser opens it, a file's header when the file is asked for by name. Against "a flat list of 256 files"
   (still a limit, a long list, an 18 s scan at start) and "raise 32 to 64 now" (no browser).
52. **Browser = a full-screen list with the overview and audition.** The folder's sub-folders, then its samples, sorted by name; the
   highlighted sample's waveform and length on top; the highlighted sample plays from the pad keys. Against a list without audition and

**As built (2026-10-11; 219 engine tests in the 6 configurations (the whole matrix once, then the pads tests again after a fix of the
new test's thresholds), 102 UI tests, simulator + firmware built, RAM 66.0 %; `tools/sample_sim_check.cpp` run on the simulator's card
of 155 files; NOT flashed, NOT tried by the user: the board's card code was only compiled):**
- **A sample's name is its path below the samples folder, without ".smp"** ("Drums/Kicks/808 long"), at most 47 characters
  (`AUDIO_NAME_MAX` = `PAD_NAME_MAX` 48; it was 24). pads.cfg, the history and the jobs keep working by name: a version (`name~n`), a
  crop or a stretch lands in its source's folder; a recording (`recN`) in the root. A path longer than 47 characters is listed by the
  browser but cannot be taken ("cannot be read").
- **The catalog holds the files in use** (`AUDIO_SAMPLES_MAX` 32, unchanged: it is also the number of loaded samples). `hal_audio.h`:
  `audio_sample_find(name)`, `audio_sample_use(name)` (reads the header from the card when the file is not in the catalog: -1 no such
  sample, -2 the catalog is full), `audio_dir_open(dir)` / `audio_dir_read(first, out, max)` (one folder, sorted, folders first,
  versions left out; the platform keeps the list: PSRAM on the board, 320 entries at most, a longer folder shows its first 320).
  `audio_samples_rescan` is gone. The engine side (`sample_catalog.h`): `engine_synth_catalog_find / _add / _remove`.
- **An entry nothing uses leaves the catalog when it is full** (`app.c` `sample_use`: no pad, no rack sampler, no job refers to it), and
  **its sample is unloaded** (new: samples were never unloaded). Safe unload: `engine_synth_catalog_remove` only clears the name;
  `engine_synth_housekeeping` unloads once 4 engine blocks have passed (every command sent before the removal has reached the audio
  thread) and `SampleBank::can_unload` says nothing reads it (loaded, no head read in flight, not being scanned, no stream on it: a
  voice that still plays it keeps it). Then the next file takes the entry's index. `StorageDevice::forget` gives the file handle back
  (the board's table of 48 paths would fill; handles are counted, a file can be loaded again while its old copy waits to be unloaded).
  Test `pads_catalog_entry_leaves_and_its_sample_is_unloaded_once_nothing_plays_it`: the voice is not cut, 49 KB come back, the index
  is reused.
- **The pads' files enter the catalog one per app step** (`pads_resolve`: after a start, a card change, pads.cfg, a version picked);
  a pad whose file is not on the card is not asked for again until it or the card changes. The first switch to the Pads section after
  a start can find pads silent for a moment (16 files: about 0.1 .. 0.2 s on the board, estimated).
- **The browser** (`scr_browse.c`, over either section): opened by the pad editor's Smp row (a turn of encoder B or a push; the row no
  longer steps through files) and by the SAMPLES tab's File row (the Scan row is gone). Up / down by the joystick or either encoder,
  Page - / + by a screen; a push or right opens a folder, left or the ".." row goes to its parent; a push on a sample chooses it,
  Back cancels. It opens on the folder of the current file with that file highlighted. Header: the folder, and "row / rows".
- **Audition (Pads)**: 150 ms after the highlight rests on a sample, its header is read (the overview appears) and **the pad takes
  it at once**, so every pad key plays it on that pad, with the pad's level, tune, filter and FX bus. Back puts the pad back exactly
  (its old file and trim). No extra voice and no new engine path: it is an ordinary pad change.
- Chosen by me (say if one is wrong): a file taken through the browser plays whole (Start, End and the loop start go back to the
  file's ends; mode, level, tune, filter, bus and the rest stay), where the old Smp stepping kept the trim frames of the previous
  file; the pad keys all play the browsed pad while the browser is open (no selection change); the SAMPLES tab's browser has no
  audition (the synth plays the rack, not a file); versions are not listed (the EDIT page reaches them); `.wav` / `.mp3` are listed
  in the simulator only (converted when taken); the serial `samples` command first takes the root folder's files into the catalog
  (the board test tools pick from it).
- Changed formats (no saved content to keep: user, 2026-10-09): history.cfg delimits its names (`v <seq> |name|parent| ...`: a name
  with a space cut the line before); pads.cfg `file` holds the path.
- Risks / limits: **32 different samples in use at once** is still the limit (64 pads cannot all hold a different file; the popup
  "LIBRARY Full: 32 samples in use"); raising it costs internal RAM (about 200 bytes per entry plus the bank's slot). pads.cfg must
  fit 4 KB and a path is longer than a name: 64 pads with long paths can pass it (the end is cut silently: known debt, a file per bank
  would fix it). Reading a 300-entry folder holds the card for about 0.1 s (estimated; the loader is pumped every 16 entries). A long
  name is cut at the row's edge (the highlighted row shows its end). Firmware RAM: the names grew (+1.5 KB pads, +1.5 KB history,
  +0.8 KB catalog, +0.8 KB card paths, +1 KB browser) and the board's second catalog copy went (-5.6 KB).

## Known limits and ideas for later

- Not hooked to the UI yet: the **Sampler** and **Granular** modules and the sample bank (stage 6 is engine-level and
  tested; the application needs a sample browser, a rack module type and loading from the TF card).
- **ESP32**: runs on the first prototype (ADR-035). Display, keyboard, knobs, I2S audio, power and serial debugging work; the TF card, the LED driver and a speaker-amp check are still open. Remaining performance work is listed in CONTINUE.md.
- q15 tail noise floor of the reverb (about -84 dBFS), the naive shapers (no anti-aliasing, ADR-013), the 512-point FFT
  (needs 1024 above 48 kHz), mono-only samples, no ADPCM.
- Block-rate envelopes; a cable into a parameter that the module reads once per block is stepped per block.
- Candidates: per-voice filter keytracking, LFO tempo sync, a patchable FX rack, bypassing idle effects to save CPU,
  PIE (SIMD) kernels for the S3 behind the existing block functions. (Bypassing idle effects was done in ADR-035.)

## Guidelines (enforced)

1. The audio path never calls `new`/`malloc`, takes a lock, or logs. *Why: determinism.*
2. No `float`/`double` in the audio path; floats only at init, control rate or in tests. *Why: FPU-less targets, bit-exact tests.* **Exception (ADR-035, user decision): the ESP32-S3 has a single-precision FPU; the filter tick and the vowel / dust filters use float32 where it measured 8x faster. Anywhere else, measure first.**
3. Every saturating/rounding rule lives in `q.h`; modules do not hand-roll shifts. *Why: one place to get scaling right.*
4. Every DSP module ships with a host test (SNR vs float64 reference, plus stability at extreme parameters).
5. Time-based parameters are derived from `kSampleRate`/`kBlock`. *Why: ADR-004.*
6. Code is marked `[AUDIO]`, `[CONTROL]` or `[INIT]` when the context is not obvious.
