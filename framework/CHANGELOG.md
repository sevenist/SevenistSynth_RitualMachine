# Update log: the framework and the repo

What changed in the library (`framework/`) and in the repo as a whole. Each app keeps its own update log.

## 2026-11-15: switch groups

- `modular/patch.h`: `Group`, `Selector`, `Node::group`; `make_group`, `ungroup`, `add_selector`; `patch_switches`, `switch_row`,
  `groups_on`. The list gets a SWITCHES section after MACROS. The text form has `selector` and `group` lines and a node's `@<group>`;
  an older reader skips them.
- The runner skips a group switched off. A bypass group's exits get what came into the group; a selector's other groups send silence.
- `modular/cost.h`: a selector's groups count as their dearest.

## 2026-11-15: the engine types measured; the wallet prices an engine synth

- `modular/module_costs.h`: an `engine` column, each catalog module as an engine type (engine_modules.h) on HWV1. The wrapper adds
  about 1 300 cycles a block plus about 300 per port (Osc 2 049 -> 3 994, ADSR 1 578 -> 3 046, VCA 446 -> 2 272).
- `modular/cost.h`: `PatchCost::engine_total` (with `engine_voice`, `engine_fx`) is the patch exported as an engine synth. It errs on
  the safe side: the default patch at 3 voices is estimated at 62 000, measured at 57 598.
- `modular/engine_modules.cpp`: one shared host for every type (64 copies in internal RAM did not fit the board); a type's
  description is made when it is registered.

## 2026-11-15: the catalog's modules in the engine

- `modular/engine_modules.h` (new): every catalog module (the In / Out ones aside) is an engine module type, "F" + its name (FBody,
  FOsc, FADSR ...). It keeps its float code and features, with q15 ports. Each one nulls against the modular runner between -66 and
  -99 dB (`tests/test_modular_types.cpp`). `register_modular_types(reg)`, or `register_modular_type(reg, "Body")` alone.
  `modular_type_id`, `modular_def_of`. The adapter skips them, so the studio does not list them twice.
- `engine/core/module.h`: `ProcessCtx::silence` (what an unplugged input reads); `Registry::kMax` 128 -> 192 (ids 128..191: the
  catalog's).
- `tools/build_engine_tests.ps1` also compiles `modular/catalog.cpp`, `patch.cpp`, `engine_modules.cpp`.
- ADR-049 addendum 7.

## 2026-11-15: lighter envelopes and Osc; the engine's modules measured

- `modular/modules.h`, measured on HWV1 in cycles per block (before -> now). The output changes slightly, a choice the user made
  ("free").
  - **Osc 8 160 -> 2 047.** It reads its Pitch input at the block's two ends and glides between them (FM stays per sample), and has
    one loop per wave.
  - **ADSR 2 365 -> 1 573.** Its rates are recomputed only when a value changes, and a resting block is filled at once. Cold:
    26 542 -> 2 293.
  - **Perc 7 742 -> 2 022** (Power law 11 454 -> 2 642). It is evaluated every 8 samples with lines between.
  - **LFO 3 151 -> 1 529.** It is evaluated every 8 samples; a square's or an S&H's step becomes an 8-sample line.
- `modular/mdsp.h`: `decay_coef` uses `fast_exp2`, not `expf`, whose code sat in flash. That makes every envelope, compressor, gate
  and smoother cheaper when the cache is cold (Comp3 cold 49 361 -> 6 597, Glue 58 792 -> 9 362). `sin01`, `poly_blep` and
  `fast_log2` are `SC_HOT`.
- `modular/engine_adapter.cpp`: the registration's scratch is 1 MB on the board (16 MB on the desktop) and is given back after.
- `modular/module_costs.h`: 65 modules, the 33 engine modules ("RM ...") included. They were measured through the adapter by
  apps/synthlab's `hwv1_bench_rm`, conversion included, which costs about 1 300 cycles a block a module.

## 2026-11-15: the cycles wallet

- `modular/cost.h` (new): `patch_cost(patch, voices)` adds a patch up from `module_costs.h`. It counts the engine's fixed cost, each
  voice (the VOICE area's modules, a module at its slowest value at its worst, its cables, the engine's share) and the FX area once.
  It also reports the slowest-values total, the modules' state bytes and the modules not measured. `node_cycles`, `cable_cycles`
  and `voices_in_budget` come with it. Checked on HWV1: within 1.3 % of a generated synth's measured cost.
- `modular/patch.h`: `Patch::voices` (1..`kMaxPatchVoices` = 6) is the synth's voice count, set by the patch's designer. The text
  form has a `voices N` line; an older file has none and gets 6, and a count out of range is skipped.
- `engine/core/engine.h`: `set_voice_mode(mode, legato, glide_ms, max_voices = 0)`. Poly then plays on the first `max_voices` voices
  only (it steals among them), with no reload and no memory change. 0 means all voices. Test:
  `a_voice_cap_keeps_poly_on_fewer_voices_without_a_reload`.

## 2026-11-15: the modules' cost on the board

## 2026-11-15: a sound as text

- **`control/preset.h`** (new, C, header only): a synth's sound as text, its values by path (`value BODY/Tune 50`; "SECTION/Name",
  the section being the `PARAM_HEAD` before the value, in quotes when it holds a space) and its macros (`macro`, `dest`, `link`
  lines, control/macro.h). Values by name, not by place: a synth that gains, loses or reorders values still reads its sounds, so a
  sound made in SynthLab Studio loads on a board whose engine was exported (and fixed) since. `pset_to_text` / `pset_from_text` over
  any list of `param_desc_t` (the app reads and sets its values), the words and lines (`pset_word`, `pset_line`: quoted words, CRLF),

  (new).

## 2026-11-14: macros, and a macro that drives another

- **`control/macro.h`** (new, C, header only): one control that moves several targets, each through a mapping (`ctl_map_t`: a
  target, Min / Max 0..1 of its range, a curve); a macro (`mac_t`) has up to 8 destinations, and one can be another macro of the set
  (`MAC_KIND_MACRO`): it sets that macro's position, which moves that macro's destinations, down the chain. `mac_add` refuses a link
  that would loop; `mac_apply` walks the chain and calls the app's function for every other target (what a target is stays the app's:
  `ctl_target_t` is its key). The Ritual Machine's macros, joystick axes and Shift / Mod mappings use it (its `macro_t`, `mapping_t`,
  `macro_def_t`; Min / Max were whole percents, now floats that hold the same values: checked against the old code over every range,
  curve and knob value, 2,052,972 comparisons, none differ), and so do SynthLab Studio's macros. Both apps can now link macros (the
  Ritual Machine's MACROS tab, Add; Studio, a macro's handle dropped on another). `tests/test_macro.cpp` (new).
- `control/curve.h`: adding a point to a curve with no points is refused (a compiler warning; such a curve never exists).

## 2026-11-14: response curves

- **`control/curve.h`** (new, C, header only): the response curves a knob's travel goes through. Lin, Exp, Log, S built in (33-point
  tables, linear interpolation); user curves U1..U8 (2..16 points, linear or stepped segments) in a `crv_bank_t` the app owns; their
  text (`curve` / `point` lines). The Ritual Machine's `curves.c` is its bank and its file on the card (its `curve_*` calls unchanged;
  checked against the old file under 4,000 random edits, 477,546 comparisons, none differ). SynthLab Studio's own Exp / Log / S
  formulas are gone: its macros now read the board's tables, the shapes the Ritual Machine plays (at most 0.03 of a range from the
  exact formulas it had, at the top of Exp). `tests/test_curve.cpp` (new).

## 2026-10-13: the repo is a library and its apps

Commits `ffaa378` to `0ab1696` ("app separation", phase 1 to step 2c).

Until now this repo was one program, the Ritual Machine. It is now a library, `framework/`, and the apps built on it,
`apps/`. The Ritual Machine is the first app. A new synth starts from a template with one command, runs on the desktop
and on the first prototype from the same source, and copies nothing from the library.

### Start your own synth

```powershell
.\tools\new_project.ps1 my_synth       # makes apps/my_synth from the template
.\build.ps1 -App my_synth              # its desktop program
.\run.ps1 -App my_synth                # two windows: the screen, and the board's front panel
C:\.platformio\penv\Scripts\pio.exe run -d apps/my_synth -t upload     # firmware for the first prototype
```

The template is a four-voice synth (saw oscillator, low-pass filter, one envelope) with a screen and the board's keys.
What you edit:

| File | What it holds |
| --- | --- |
| `src/synth.cpp` | Your sound: which engine modules, how they are cabled, the values a control can move |
| `src/app.cpp` | What each control does and what the screen shows |
| `src/main_sim.cpp`, `src/main_esp32.cpp` | The two entry points: memory for the engine and the main loop |
| `build.ps1`, `platformio.ini` | The desktop build and the firmware build |

`apps/my_synth/README.md` says where to change things: another sound, more voices, a value on a control, another
board.

### What the library gives an app

| Part | Include as | What you get |
| --- | --- | --- |
| The DSP engine | `engine/...` | The modular graph: oscillators, filters, envelopes, effects, samplers. It includes nothing from an app |
| The board interface | `hal/...` | Display, controls, key LEDs, small files on the card, battery, large memory, audio output |
| The drawing kit | `ui/gui.h`, `ui/popup.h` | Layout rectangles, text, fields, sprites and popups on a u8g2 display |
| The first prototype | `boards/hwv1/` | Its drivers behind the board interface |
| The desktop | `boards/desktop/` | The same interface on a PC: SDL windows, keyboard, mouse, audio, the card as a folder |

Three things work differently from a classic "one firmware" layout:

- **Audio is a callback.** The library owns the output; your app owns its engine and hands over one function,
  `audio_out_start(synth_render, sample_rate)`. The board calls it for every buffer.
- **Each board lists its own controls.** `input_controls()` returns a table: for each control its name, its kind (key,
  button, encoder, pot without end stops, knob, joystick axis), its place in the key matrix, its place on the panel,
  and whether it has an LED. An event says "control number N was pressed, turned or moved". An app that reads only
  the kind and the place, as the template does, runs on any board with no change.
- **An app that wants named controls keeps its own list and a map per board.** The Ritual Machine does this: its
  roles (Enc A, column knob 1, key row.column ...) are in `core/controls.h`, and one small file per board says which
  board control plays which role (`core/boards/map_hwv1.h`, `map_panel.h`). Swapping two pots is one row of the map.

### Try an app as either board on the desktop

The simulator's panel window is now drawn from a board's control table, so the desktop program can be built as any
board the library knows:

```powershell
.\build.ps1                  # the panel: the future prototype (4 key columns, 2 encoders, 8 knobs, joystick)
.\run.ps1
.\build.ps1 -Board hwv1      # the first prototype (4 function keys, 4 x 8 keys, 7 pots without end stops, joystick)
.\run.ps1 -Board hwv1
```

- Each board is its own program (`oled_sim.exe`, `oled_sim_hwv1.exe`) with its own objects. After a change, build the
  board you run; `run.ps1` prints a note when the program it starts is the older of the two.
- `-App` and `-Board` combine: `.\build.ps1 -App my_synth -Board hwv1`.
- The app sees the simulated board exactly as it sees the real one: the same table, the same board name.
- Every part works with the mouse (click, wheel, drag; right click on the joystick is its push). Each part shows the PC
  keys that work it. Keys are given by a part's kind and place: matrix keys take the block `F1`.. / `1`.. / `Q`.. /
  `A`.. / `Z`.., what turns takes a pair each starting with `[ ]` and `; '`, the joystick takes the arrows.

### Add a board

1. A folder in `framework/boards/` with the board interface behind it, its control table, and its name
   (`input_board_name()`).
2. In the app's `platformio.ini`, the folder in `build_src_filter`.
3. To draw it on the desktop: a branch in `framework/boards/desktop/sim_board.h` and an entry in `Get-SimBoard`
   (`framework/tools/sim_build.ps1`). The panel window needs nothing else: it draws each line of the table at its place.
4. For an app with its own roles: a map file for the board (the Ritual Machine: `core/boards/map_<board>.h` and a line
   in `core/controls.c`). Without a map, the board's matrix keys still play.

### What changed for existing work

- **Paths.** The Ritual Machine's `src/`, `tests/`, `tools/`, `assets/`, `sdcard/`, `samples_src/` and `platformio.ini`
  are now in `apps/ritual_machine/`. There is no `platformio.ini` at the repo root: build the firmware with
  `C:\.platformio\penv\Scripts\pio.exe run -d apps/ritual_machine`. In VS Code, open `oled_sim.code-workspace` so the
  PlatformIO extension finds each app.
- **Commands.** `.\build.ps1`, `.\run.ps1` and `.\test.ps1` stay at the root and default to the Ritual Machine.
  `.\test.ps1` runs the library's tests, then the app's engine and UI tests.
- **The board interface.** `hal_input.h` has no shared control list any more: events and LEDs carry the board's own
  control ids. `hal_audio.h` is gone from the library: the output is `hal_audio_out.h`, and the Ritual Machine's engine
  calls are its own `core/audio.h`.
- **The card.** Each app declares its own folders; the library creates what is declared and knows no layout.
- **The simulator's panel.** It has 4 key columns, like the board it draws. The PC keys `F5`-`F8`, `5`-`8`, `T`-`I`,
  `G`-`K` and `B`-`,` do nothing there any more: use `-Board hwv1` for 8 columns. The octave is Shift + joystick
  up / down. The joystick's push is a right click on the stick, or Right Ctrl.
- **Saved settings are untouched.** The Ritual Machine's roles kept their values, so `ui.cfg`, `keys.cfg`, bindings,
  key layouts and presets read as before.

### Limits today

- The panel places of the first prototype's pots and joystick are estimated, not measured. The drawing with
  `-Board hwv1` shows the right parts, not yet their exact positions (`framework/boards/hwv1/hwv1_controls.c`).
- Still the Ritual Machine's, not the library's: its declarative screens, bindings, key layouts and layers, and its
  sample library. Another app that wants samples writes its own "find the file, hand it to the sampler".
- Apps do not share a sample folder on the card. Two firmwares used with one card can write the same file names.
- The simulated pots without end stops report clean steps or positions; the real board's noise thresholds are not
  simulated.
